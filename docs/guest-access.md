# 공개 게스트 체험

`POST /api/v1/auth/guest`는 로그인 없이 호출한다. 응답은 기존 `TokenResponse`이며
`user.role=GUEST`, refresh token은 기존 HttpOnly 쿠키에만 저장한다.
클라이언트가 보낸 계정 ID·기기 키·별명을 계정 식별자로 사용하지 않는다.
유효한 쿠키가 있으면 그 세션을 유지하고, 없으면 서로 다른 사용자·가족·아이·완료된 예시 프로필을 생성한다.
기존 카카오 세션도 게스트 호출로 교체하지 않는다.

## 격리와 권한

- API는 기존 토큰·프로필 소속·대화/활동 소유권 검사를 그대로 거친다.
- 다른 PC/브라우저 프로필은 독립적이다. 같은 브라우저 프로필의 탭은 쿠키를 공유한다.
- 서버에서 허용한 체험 경로만 접근할 수 있다. 보호자 연결, 공유 요청, 커뮤니티 변경,
  외부 푸시 등록, 데이터 내보내기, 디버그 초기화는 게스트에게 허용하지 않는다.
- 일반 게스트의 `is_tester`는 false다. 기존 AI 동의·데이터 처리 조건을 우회하지 않는다.
- 카카오 로그인 시 게스트 기록을 이관하지 않는다.

## 티키와 만나기와 보호자 동의

- 일반 로그인·게스트 진입 후 프론트 `/welcome`에서 필요한 동의를 먼저 받는다.
  게스트는 기본 체험으로 건너뛸 수 있지만, ‘티키와 만나기’에는 동의가 필요하다.
- 신규 일반 계정도 `/me`에서 미완료 빈 프로필과 소속을 준비한다. 이 프로필에 동의를 남기고,
  첫인사 완료 시 같은 프로필을 채운다. 준비만으로 첫인사를 완료 처리하지 않는다.
- `GET /api/v1/first-greeting/readiness`는 동의·AI 설정을 확인하며 외부 AI 호출이나 사용량 소비를 하지 않는다.
  사용 불가 시 프론트는 이유와 재확인 버튼을 표시한다.
- 보호자가 개인정보 처리·AI 대화 동의서의 현재 버전을 각각 읽고 체크한 뒤,
  보호자임을 직접 확인해야 한다. 서버도 `guardianConfirmed=true`와 문서 버전을 검사한다.
- 동의는 게스트 본인의 프로필에만 저장한다. 문서 버전·동의 주체·시각을 기록하며 다른 게스트와 공유하지 않는다.
- `privacy_child`, `ai_conversation` 두 동의가 모두 유효할 때만 실제 AI를 허용한다.
  AI 사용 설정·사용량 제한도 그대로 적용한다. 음성 기능과 다른 목적의 동의는 게스트에게 열지 않는다.
- 상단 ‘보호자 동의’(`/guest/consent`)에서 철회하면 이후 AI 요청을 서버에서도 차단한다.
  동의하지 않아도 기존 기본 체험은 계속할 수 있다. 문서가 개정되면 다시 동의해야 한다.
- 이 흐름은 보호자의 자기 확인이다. 보호자 신원·관계의 본인인증 기능은 포함하지 않는다.
  동의서는 기존 법률 검토 전 초안을 표시한다.

## 만료와 제한

- 최초 생성부터 24시간 후 만료한다. refresh를 회전해도 기한을 연장하지 않는다.
- access token이 아직 남아 있어도 계정의 절대 만료 시각을 검사한다.
- 신규 게스트 진입 시 만료 계정을 최대 10개씩 관련 기록과 함께 삭제한다.
  방문이 없으면 정리가 지연되므로 정확한 시각의 삭제가 필요하면 `guests.purge_expired`를 정기 실행해야 한다.
- DB의 `guest_rate_limits`에서 UTC 날짜별로 신규 계정 전체 1,000개,
  게스트별 변경 요청 300회, 전체 변경 요청 10,000회로 제한한다.
  조건부 UPSERT이므로 서버리스 인스턴스가 달라도 합산한다. 한도 초과 시 429를 반환한다.
- 로그아웃과 조회는 변경 요청 한도에 포함하지 않는다. 이전 사용량 행은 신규 진입 시 정리한다.

## 배포

백엔드를 먼저 배포하고 프론트를 배포한다. 기존 실제 API 모드(`VITE_USE_API=true`)를 유지한다.
`AUTH_DEV_LOGIN`을 켤 필요가 없다. 운영 환경에서는 `AUTH_COOKIE_SECURE=true`와 HTTPS를 사용한다.
신규 `guest_rate_limits` 테이블은 기존 `init_db/create_all` 경로로 생성된다.
운영 DB 계정에 테이블 생성 권한이 없다면 배포 전 해당 테이블을 생성해야 한다.

기존 DB의 `ck_users_role`이 `CHILD`·`GUARDIAN`만 허용하면 게스트 생성은 500으로 실패한다.
`create_all()`은 기존 CHECK 제약을 변경하지 않으므로 아래 이관도 필요하다.

- 로컬 SQLite: `python tools/migrate_guest_role_sqlite.py`. 기존 DB 전체를 `data/*.before-guest-*.db`로
  백업하고 모든 계정·참조·인덱스를 보존하며 `GUEST`를 추가한다. 재실행은 변경 없이 종료한다.
- PostgreSQL: `migrations/006_guest_role.postgresql.sql`을 배포 전에 적용한다.
  이 SQL은 기존 계정과 기록을 삭제하지 않는다. 로컬 SQLite 이관은 운영 PostgreSQL에 적용되지 않는다.

검증: `python -m pytest tests/test_v1_guests.py tests/test_v1_auth.py`
